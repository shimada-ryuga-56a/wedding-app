# dev-task：1つのタスクを最初から PR まで進める

このスキルは、私が設計を理解しながら実装することを最優先にする。
速く終わらせることより、各フェーズで私が「なぜそう作るのか」を説明できる状態にすることを優先する。

全体の流れ：

1. タスクを読む
2. グリルで詳細を詰める（grill-me）
3. フェーズ計画とテスト項目表を docs リポジトリに作る
4. フェーズを1つずつ実行する
5. テストを仕上げる
6. 学習メモを残す
7. PR を作る（pr スキル）

各ステップの終わりで、私の「OK」を待ってから次へ進む。

---

## 1. タスクを読む

- `gh issue view <番号>` で Issue を読む
- 依存タスクが終わっているか確認する。終わっていなければ私に伝えて止まる
- 作業ブランチを切る：`git switch -c <番号>-<slug>`（例：`12-rsvp-form`）
- docs リポジトリに作業フォルダを作る：`../wedding-app-docs/tasks/<番号>-<slug>/`

## 2. グリルで詳細を詰める

- `grill-me` スキルを使い、この Issue の詳細を詰める
- 特に詰める観点：
  - 完了条件があいまいでないか
  - オニオンアーキテクチャのどの層に何を置くか
  - 単体テストで確かめることと、E2E で確かめることの切り分け
  - この Issue の範囲外にすること
- 終わったら、決定事項を plan.md の「決定事項」節に書く

## 3. フェーズ計画とテスト項目表を作る

`templates/` のテンプレートを使って、次の2つを作る。どちらも `natural-japanese` スキルに従って書く。

- `../wedding-app-docs/tasks/<番号>-<slug>/plan.md`（フェーズ計画）
- `../wedding-app-docs/tasks/<番号>-<slug>/test-cases.md`（テスト項目表）

フェーズ分割のルール：
- **最大20フェーズ**。少なく済むなら少なくてよい
- 1フェーズは「解説1つ＋実装1まとまり」。1フェーズで新しい概念は1つまで
- 各フェーズに、私が書く穴埋め箇所があるかどうかを明記する
- 穴埋め箇所は、設計・概念の理解につながる箇所だけにする
  - 向いている：依存の向きを決める import、インターフェースの定義、ドメインルールの判定、テストの期待値
  - 向いていない：設定ファイル、型定義の羅列、ボイラープレート、構文の細部
- テストを書くフェーズを、実装フェーズの直後か直前に置く（テストを最後にまとめない）

作成後、docs リポジトリでコミットする（commit スキルの規約に従う）。
例：`docs(#12): フェーズ計画とテスト項目表を追加`

私が plan.md と test-cases.md を確認し、OK を出してから実装に入る。

## 4. フェーズを1つずつ実行する

1回のやりとりで進めるのは **1フェーズだけ**。

各フェーズの進め方：

1. **解説**
   - このフェーズで何を作るか、なぜそう作るかを説明する
   - 設計・概念を中心に、スモールステップで説明する。構文の説明はしない
   - 必要なら、図（テキストの依存関係図など）を使う
2. **実装（あなた）**
   - 穴埋め箇所以外のコードを書く
   - 穴埋め箇所は次の形で残す
     ```ts
     // TODO(you): <何を書くか>
     // ヒント: <考える観点。答えそのものは書かない>
     ```
   - 穴埋めが残っていても型チェックが通らないことがあるが、そのままでよい
3. **実装（私）**
   - 穴埋め箇所の場所と数を伝え、私が書くのを待つ
4. **レビュー**
   - 私が書いたコードを読み、設計の観点でフィードバックする
   - 文法・型・lint のエラーは、許可を取らずに直してから「直した箇所」を伝える
   - 設計の誤りは、直さずに理由を説明し、私に直してもらう
5. **確認**
   - 型チェック・lint・関連テストを実行し、結果を伝える
6. **記録とコミット**
   - plan.md の該当フェーズにチェックを入れ、「学んだこと」を1〜3行で追記する（私の言葉を優先する）
   - アプリ側は commit スキルでコミットする
   - docs 側の更新もコミットする

途中で設計の前提が崩れたら、実装を止めて私に相談し、plan.md を更新してから再開する。

## 5. テストを仕上げる

- test-cases.md の全項目について、テストが実装されているか確認する
- 単体：`npx vitest run`
- E2E：`npx playwright test`
- 結果を test-cases.md の「結果」列に反映する
- 失敗したテストは、原因を説明してから直す（設計の問題なら私に相談する）

## 6. 学習メモを残す

- `templates/learning.md` を使って `../wedding-app-docs/tasks/<番号>-<slug>/learning.md` を作る
- このタスクで出てきた概念のうち、今後も使うものは `../wedding-app-docs/concepts/<概念名>.md` に追記または新規作成する
  - 例：`concepts/onion-architecture.md`、`concepts/dependency-inversion.md`
  - 既にある場合は、今回の具体例を追記する
- `natural-japanese` スキルに従って書く
- docs リポジトリでコミットし、push してよいか私に確認する

## 7. PR を作る

- `pr` スキルで PR を作る
- PR 本文に、docs リポジトリの plan.md・test-cases.md・learning.md へのリンクを入れる

---

## 注意

- 一度に複数フェーズを進めない。私が「まとめて進めて」と言ったときだけ例外とする
- 解説に確認問題や一問一答を勝手に付けない（私が頼んだときだけ）
