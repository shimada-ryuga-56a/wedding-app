# commit：意味のまとまりごとにコミットする

## 手順

1. 状態を確認する
   - `git status`、`git diff`、`git diff --staged` を実行する
   - 現在のブランチを確認する。`main` にいる場合はコミットせず、私に伝えて止まる（docs リポジトリは `main` への直接コミットでよい）
2. コミットに含めないものを確認する
   - `.env`、認証情報、AWS のアクセスキー、Stripe のシークレットキー、`cdk.out/`、`node_modules/` が含まれていないか確認する
   - 見つけたら、コミットせずに私に伝える
3. コミット前のチェック（アプリリポジトリのみ）
   - 型チェック・lint を実行する。エラーがあれば直してから進む（軽微な修正は許可不要）
   - 穴埋めの `TODO(you)` が残っている場合は、コミットしてよいか私に確認する
4. 変更を分ける
   - 1コミット＝1つの意味のまとまり。異なる目的の変更が混ざっていたら、ファイル単位で分けてコミットする
5. メッセージを書いてコミットする
   - コミットメッセージに`Co-Authored-By: Claude`などを書いてはいけない。

## メッセージの形式

```
<type>(#<Issue番号>): <要約>

<本文：必要なときだけ。何を、なぜ変えたか>
```

- 要約は日本語で、20文字程度まで。文末に句点を付けない
- 本文は日本語で、50文字程度まで。
- Issue 番号はブランチ名から取る。わからなければ省略する
- 本文には「なぜ」を書く。「何を」は差分を見ればわかるので短くする

type の種類：

| type | 使う場面 |
|---|---|
| feat | 機能の追加 |
| fix | バグ修正 |
| refactor | 振る舞いを変えない設計・構造の変更 |
| test | テストの追加・修正 |
| docs | ドキュメント |
| infra | CDK・AWS 構成の変更 |
| ci | CI/CD の変更 |
| chore | 依存関係の更新、設定変更など |

例：

```
feat(#12): 参加表明をドメインモデルとして表現

参加可否とメールアドレスの組み合わせルールを domain 層に閉じ込め、
フォームやDBの都合から独立させるため。
```

## 注意

- コミットは自由に行ってよいが、`git push` は必ず私に確認する
- `--amend`、`rebase`、`reset --hard` などの履歴の書き換えは、私の指示があったときだけ行う
- GitHub の草に反映させるため、コミットのメールアドレスが GitHub アカウントに登録したものと一致しているか、最初の1回だけ `git config user.email` で確認する
